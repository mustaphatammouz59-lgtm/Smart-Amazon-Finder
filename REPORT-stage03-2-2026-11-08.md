## 2. JWT verification architecture (`app/lib/access.ts`, `app/lib/auth.ts`)

- `requireAdmin` no longer trusts any plaintext header. It requires
  `Cf-Access-Jwt-Assertion` and passes it to a verifier; identity (email) is
  derived **only** from verified claims, then resolved against `admin_users`
  and the unchanged RBAC matrix. If the plaintext email header is present and
  disagrees with the verified claim, the request is rejected.
- **Configuration is server-side only**: Worker vars `ACCESS_TEAM_DOMAIN`
  (issuer) and `ACCESS_AUD` (application audience tag), read from env — never
  from the request. If either is missing, the guard fails closed (401 for
  every admin request). No secrets are hardcoded; neither value is a secret
  (they are identifiers), but both are owner-set at deploy time. A loopback
  `http://127.0.0.1` issuer is accepted **only** to make local verification
  possible; production configuration uses the `https://` team domain.
- **Verification (Web Crypto, zero dependencies)**: token split into 3
  segments; header `alg` pinned to **RS256** (rejects `none` and HMAC
  confusion); `kid` required; JWKS fetched from
  `{issuer}/cdn-cgi/access/certs` — a URL built exclusively from the
  configured issuer; RSA key imported as `RSASSA-PKCS1-v1_5` + SHA-256;
  signature verified over `header.payload`; then claims: `iss` exact match,
  `aud` (string or array) must contain the configured audience, `exp` must
  be in the future, `nbf` (if present) must not be in the future, `email`
  claim required.
- **JWKS cache & rotation**: keys are cached in the isolate for 10 minutes.
  An unknown `kid` triggers **exactly one** forced refresh — this is what
  makes Access key rotation work without a redeploy. Verification results
  and identities are never cached.
- **Failure behaviour**: every failure mode (missing, malformed, bad
  signature, wrong issuer/audience, expired, not-yet-valid, unknown key,
  JWKS unreachable, config missing) returns the same generic
  401 UNAUTHENTICATED envelope; the specific reason is written to server
  logs only. JWTs, headers and claim values are never logged.

## 3. Cryptographic verification test results

Tests use **real RSA keypairs and real RS256 signatures** (Web Crypto in the
test process); only the JWKS HTTP fetch is stubbed. All pass:

- Valid token → identity derived; aud accepted as string or array.
- Malformed tokens (wrong segment count, bad base64, empty) → 401.
- Signature by a different key (kid spoofed to the real key) → 401.
- Tampered payload (forged email claim) → 401.
- Expired → 401; future `nbf` → 401.
- Wrong issuer → 401; wrong audience → 401.
- `alg=none` (unsigned) → 401; `alg=HS256` → 401.
- Unknown kid → 401 after **exactly one** JWKS refresh (fetch count asserted).
- Key rotation: cache warmed with key-1; JWKS then serves only key-2; a
  key-2 token verifies after the refresh (fetch count 2).
- JWKS cache: two verifications → one fetch.
- JWKS retrieval failure → 401 (fail closed).
- Token without an email claim → 401.
- Guard level: no-JWT → 401; **spoofed email header with no JWT → 401**;
  valid JWT + mismatched email header → 401; unconfigured Access → 401;
  valid JWT with no admin record → 401; valid editor JWT publishing → 403;
  valid owner JWT → passes.
- **End-to-end in real workerd** (local JWKS server on 127.0.0.1, `wrangler
  dev`, real HTTP fetch of the JWKS by the Worker): no headers → 401;
  email header only → 401; forged token → 401; **valid minted JWT → 200**
  with correct admin overview; valid JWT + wrong email header → 401;
  authenticated create → 201 (publish gate + audit untouched).

## 4. POST body-size protection (`readJsonBody`, `app/lib/api.ts`)

- Cap: **16,384 bytes**, configurable per call (single shared default).
- Declared `Content-Length` is rejected up-front when over the cap; the
  actual bytes are then measured (multi-byte aware, `TextEncoder`), so a
  lying/absent header cannot smuggle an oversized body. Bodies are never
  truncated — they are rejected whole.
- Response: **413** with the new standard code `PAYLOAD_TOO_LARGE`, the
  usual envelope and a `requestId` (verified live in workerd).
- Applied to every POST endpoint that reads a body: `/api/v1/recommendations`,
  `/api/v1/gift-finder`, `/api/admin/products`. (The publish endpoint takes
  no body.) Invalid JSON under the cap still returns 400 VALIDATION_FAILED.
- Tests: exact-limit accepted, limit+1 rejected, declared-length early
  reject, multi-byte counting, invalid-JSON 400 — all pass.

## 5. Rate-limiting implementation and limitations (`app/lib/rate-limit.ts`)

- **Backend**: Cloudflare native **Rate Limiting bindings**, declared in
  `wrangler.jsonc` (`SEARCH_RATE_LIMITER` 60/min, `ADMIN_RATE_LIMITER`
  120/min; self-chosen namespace ids — the platform provisions them at
  deploy; no separate resource creation and no owner infrastructure).
  Counters are platform-managed — **not** in-memory Worker state — so
  isolate restarts and scaling do not reset them.
- **Budgets** (API-ARCHITECTURE §2 / SECURITY-PLAN §6): public search and
  discovery endpoints (`/api/v1/search`, `/api/v1/categories/:slug/products`,
  and the two finder POSTs) → 60/min keyed by `CF-Connecting-IP`; admin
  writes → 120/min keyed by the **verified admin identity**. Client-supplied
  forwarding headers are ignored for keying (tested); at the edge,
  Cloudflare sets `CF-Connecting-IP` itself.
- **Response**: 429 with the standard `RATE_LIMITED` envelope, a
  `requestId`, and `Retry-After: 60`.
- **Proven live in workerd**: a burst of 65 searches produced 200s up to the
  budget, then 429s with the `Retry-After` header (58 fresh 200s remained
  because 2 calls had been consumed earlier in the same minute — exactly
  the expected fixed-window behaviour).
- **HONEST LIMITATIONS**: (1) The native binding counts **per Cloudflare
  location** — the effective global ceiling is the budget × the number of
  locations serving traffic. This is abuse damping, not a strict global
  quota; a strict global limiter would need a Durable Object design and is
  recorded as future hardening. (2) If a binding is absent in some
  environment, the check logs loudly and allows the request (fail-open):
  rate limiting is availability protection layered under auth/RBAC, and
  failing closed on a config omission would take the API down. Both
  limitations are documented in the code header as well.

## 7. Revised deployment sequence (supersedes Stage 03.1 §8 where they differ)

The Stage 03.1 order deployed code before migrations, accepting a brief
window where the new API would 500 (tables missing). Re-evaluation: the
migrations are **purely additive** (zero destructive statements; the
current production code touches only `foundation_meta` and its bindings,
which the migrations never alter), so applying them FIRST is fully
compatible with the running Stage 02 code and eliminates the window.
The safer order — also the order proposed in this stage's brief — is
adopted, with two additions (Access vars, admin seeding position):

0. **Ground truth**: authenticated `wrangler d1 migrations list DB --remote`; stop on surprises.
1. **Create the DLQ**: `wrangler queues create smart-amazon-finder-dlq`.
2. **Configure Cloudflare Access** for `/api/admin/*` (owner identity allowlist) **and set the Worker vars** `ACCESS_TEAM_DOMAIN` + `ACCESS_AUD` from that application — the code now verifies JWTs, but Access remains the issuer and edge pre-filter; both layers are required by SECURITY-PLAN §3.
3. **Back up production D1**: `wrangler d1 export DB --remote` (valid — no FTS table exists yet) + verify + SHA-256; record the Time Travel bookmark.
4. **Apply migrations 0001–0004** via `wrangler d1 migrations apply DB --remote` (never raw execute — 0002–0004 are not idempotent). The running Stage 02 site is unaffected (verified compatibility above).
5. **Schema integrity checks**: `d1_migrations` = 4 rows; 31 tables; `foundation_meta` intact; live site + health still green on the OLD code.
6. **Seed structural data**: `fixtures/catalog-seeds.sql` remotely (idempotent). Never `dev-catalog.sql`.
7. **Publish code**: merge `stage-03` → `main`, upload the delta via the Contents API; Workers Builds deploys (DLQ exists → consumer attaches; rate-limit bindings provision from config).
8. **Seed the first admin** (`admin_users`, owner email/role) via the D1 console — only now, with Access live and the verifying code deployed.
9. **Production verification**: pages/health 200; `X-Robots-Tag` intact; `/api/v1/search` → 200 empty state; `/api/admin/overview` without Access login → stopped at Access; with owner Access login → 200; a request bypassing Access (if ever possible) with no JWT → 401 from the code layer; fixtures absent everywhere; audit row written by a test mutation.
10. **Rollback**: code — redeploy previous `main` commit; data — Time Travel to the step-3 bookmark (pre-migration production data is at most `foundation_meta`).

Compatibility notes: step 4 before step 7 is safe *because* the migrations
are additive-only — re-verified in this audit against the migration files.
The one ordering trap that remains is the backup: it MUST precede step 4,
because after 0004 the full export stops working (§6).

## 9. Security risks not yet resolved

- Rate limiting is per-location, not a strict global quota (§5) — accepted
  for launch; Durable Object limiter is the documented upgrade path.
- No WAF/bot rules were audited (owner-side Cloudflare settings, out of
  scope here); SECURITY-PLAN §2 expects managed WAF defaults at launch.
- Rate-limit bindings fail open when absent (§5) — mitigated by loud
  logging and by auth/RBAC being the real admin gate.
- User-account authentication remains unbuilt (mail-provider decision, O-standing) — no account endpoints exist to attack yet.
- The Access JWT verifier accepts a loopback `http://127.0.0.1` issuer in
  configuration for local development; production configuration must use
  the real `https://` team domain (called out in §2 and in
  `.dev.vars.example`). Worker vars are owner-controlled, so this is a
  configuration-hygiene note, not a code vulnerability.
