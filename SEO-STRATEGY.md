# Technical SEO Strategy — Smart Amazon Finder

Stage 00. Status: **IMPLEMENTED NOT VERIFIED** (strategy; measured results exist only after launch).
Date: 2026-11-08.

## 1. Foundation: server-side rendering

All indexable pages are SSR (React Router 7 framework mode — SYSTEM-ARCHITECTURE.md §3). Client-side rendering is reserved for interactive islands after first paint. No indexable content may exist only in client JavaScript. This is the platform's single most important SEO decision and it is architectural, not a later optimisation.

## 2. Metadata architecture

- One metadata builder per route type (product, category, guide, article, listing, static): title (unique, ≤ ~60 chars, keyword-first, brand suffix), meta description (unique, written by editors for guides/categories; template-built from real fields for products), canonical URL, robots directives, Open Graph + Twitter cards (image = original R2 asset or licensed image URL where permitted — never a scraped image).
- Metadata comes from the same records the page renders (no separate SEO fields that can drift), except `seo_title`/`meta_description` editorial overrides on categories and guides.
- Every page emits exactly one canonical, self-referencing by default; parameterised states (sort, filters beyond the canonical facet set) canonicalise to the base listing (see §7).

## 3. URL architecture

```
/                                   Home
/search?q=…                         Search (noindex — §6)
/product/:slug                      Product detail
/category/:slug                     Category landing
/category/:slug/:subslug            Sub-category
/compare/:token                     Shared comparison (noindex)
/alternatives/:product-slug        Alternatives for a product
/product-finder, /gift-finder       Tools (indexable landing states; result states noindex)
/buying-guides, /guide/:slug        Guides
/articles, /article/:slug           Articles
/about /contact /privacy-policy /terms /affiliate-disclosure
```

Slugs: lowercase, hyphenated, stable. Slug changes create 301 redirects recorded in a redirects table (admin-managed), never silent 404s for published URLs.

## 4. Sitemaps and robots

- `sitemap.xml` = index file referencing per-type sitemaps (products, categories, guides, articles, static), regenerated by the `sitemaps` queue job on publish events + nightly verification build.
- A sitemap contains **only** canonical, indexable, HTTP-200 URLs whose records pass the publication gates (status published + validation passed + value rules in §6). CI includes a sitemap-vs-routes diff test (SYSTEM-ARCHITECTURE.md module R).
- `lastmod` = the record's real `updated_at`. Never faked, never "now" for unchanged records.
- `robots.txt`: allows all public content; disallows `/admin`, `/api`, `/account`, `/compare/` (token URLs), faceted duplicates per §7; references the sitemap index.

## 5. Structured data (only where eligible and truthful)

| Page | Types | Hard rules |
|---|---|---|
| Product | `Product` + `Offer` **only when** we have licensed, current price/availability data to populate it truthfully | No `aggregateRating` unless licensed ratings data exists and is displayed on the page identically. No invented `review`. If price data is absent, emit `Product` without `offers`. |
| Guide/Article | `Article` with real author/publisher/dates | Author = the site's editorial identity; no fabricated person names/credentials. |
| Listings | `ItemList` of visible items | Positions match render order. |
| All pages | `BreadcrumbList` matching visible breadcrumbs | — |
| Organisation | `Organization` + `WebSite` (no SearchAction until site search is public and stable) | Name = final brand (gate D-01). |

Any structured data whose source field is missing is omitted, never defaulted. Validation: Rich Results test on templates at Stage 11 exit, then per-release sampling.

## 6. Indexation controls (the anti-thin-content system)

A page is indexable only when **all** are true (enforced by an `is_indexable` computation in the data layer, visible in admin):

- Product: published + validated + has editorial summary + ≥ 1 spec set + ≥ 1 lawful offer or a deliberate editorial-only flag + not a near-duplicate variant (variants live on the product page, not separate URLs, unless a variant has genuinely distinct content).
- Category: ≥ 5 published products + original intro copy + ≥ 1 guide or a completed "how to choose" block.
- Guide/article: published through the CMS checklist (original, reviewed, disclosure, internal links).
- Search results, finder result states, comparison token pages, account pages: `noindex, follow` always.
- Alternatives pages: indexable only when ≥ 3 alternatives with real delta data exist for that product.

This is the mechanism that guarantees "no thin or mass-generated pages": pages that cannot meet the bar exist for users (if useful) but stay out of the index.

## 7. Pagination, filters and duplicates

- Listings paginate with real links (`?page=2…`) and `rel` canonical to the paginated URL itself for page 1 vs. N handled per current search-engine guidance (each page self-canonical; the series is crawlable via links).
- Faceted navigation: one canonical facet combination per category is indexable (chosen editorially, e.g. a high-demand brand facet) — all other facet states canonicalise to the category base and are `noindex` if they create a distinct URL pattern. Filter state for *users* is unrestricted; only indexation is restricted.
- Sorting parameters never create indexable URLs.
- Duplicate prevention: variant collapsing (§6), single canonical domain (www/non-www + http→https redirects at the edge), trailing-slash policy fixed in config, no session IDs in URLs.

## 8. Core Web Vitals strategy

Budgets (p75, mobile, field data once available; lab budgets enforced in CI from Stage 02): **LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1.**

- SSR + edge caching for HTML; immutable hashed static assets; image discipline (responsive sizes, modern formats for originals, width/height always set — CLS), licensed remote images proxied through sizing where licence permits or rendered with fixed aspect boxes.
- JavaScript budget: route-level code splitting; finder/compare interactivity lazy-loaded; no third-party scripts at launch except, later, AdSense (loaded async, slots dimension-reserved — MONETIZATION-STRATEGY.md §5).
- Fonts: self-hosted, `font-display: swap`, metric-matched fallbacks.
- Monitoring: Cloudflare Web Analytics + periodic Lighthouse CI on the top templates; regressions over budget block release (Stage 14 gate).

## 9. Internal linking

- Breadcrumbs on every template (visible + structured data).
- Category → its guides, finder and top products; Guide → category, compared products, related guides; Product → category, alternatives, comparison entry, relevant guide section anchors.
- "Related" blocks are rule-based on shared category/specs (no random link wheels).
- Orphan control: the publish checklist warns when a new page has < 2 inbound internal links; the sitemap job also produces an orphans report for admin.

## 10. International (future, designed-for)

Single-market at launch. When expanding: per-market subdirectories (`/uk/…`) only if a market gets its own catalog/licences, `hreflang` generated from real alternate pages (never auto-translated placeholders), separate sitemaps per market. The schema's merchant/marketplace fields already support this.

## 11. Measurement

Search Console property from day one of public launch; weekly indexation report (indexed vs. eligible), zero-result internal search report feeding editorial, CWV field tracking. SEO success is reported as *eligible pages indexed* and *organic sessions per eligible page*, never as raw page counts — the anti-vanity rule that matches §6.
