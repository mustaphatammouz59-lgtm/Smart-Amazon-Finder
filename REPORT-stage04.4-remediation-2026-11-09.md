## 4. NF-2 — validation concurrency: design and guarantee

**Root cause (Stage 04.3 §3.3):** `runProductValidation` / `runOfferValidation` computed a verdict from data read across several statements and persisted it with an unconditional `UPDATE … WHERE id = ?`. An invalidating edit landing between the reads and the write was overwritten by the stale verdict.

**Design chosen — snapshot token over the verdict inputs, checked atomically at persist time. No migration.** A dedicated revision column was rejected as unnecessary: the token does not need storage, because it is fully derivable from the data already in the row and its child tables at read time. `updated_at` was rejected as the token (the brief's own caution): SQLite `datetime('now')` has one-second resolution, so two distinct states can share a timestamp and the guard would silently pass.

**Mechanism.** Each run is now two phases, composed by the existing `run*Validation` entry points (signatures and return shapes preserved; the result gains a `persistence` field):

- **Begin** (`beginProductValidation` / `beginOfferValidation`): one read pass captures the *complete* input set the engine reads — for products: name, slug, category_id + category existence, brand_id, licence_status, editorial_summary, valued-spec count, media count, offer count; for offers: the offer row's nine verdict-relevant fields, merchant existence, product existence, linked program status — and the verdict is computed from that snapshot and nothing else (the issue builders now take the snapshot as their only input).
- **Commit** (`commitProductValidation` / `commitOfferValidation`): a **single conditional UPDATE** whose WHERE clause re-states the snapshot — null-safe `IS` comparisons on the row's own columns, `EXISTS(...) = 0/1` for category/merchant/product existence, and correlated count/scalar subqueries for spec/media/offer counts and program status. SQLite/D1 executes one statement atomically and serializes writers, so check and write cannot interleave; there is no read-then-write gap in the new code. `meta.changes = 0` means the data moved: the verdict is **discarded**, nothing is written, and the result reports `persistence: 'data_changed_retry_required'` (the persisted path reports `'persisted'`). The run is audited either way, with the persistence outcome inside the audit payload, so the trail never claims a discarded verdict was stored. No reindex runs on a discard (this path wrote nothing; the concurrent edit already refreshed the projection in its own step).

**The brief's eight guarantees, mapped:** (1) snapshot captured in the same read pass that feeds the computation; (2) verdict computed from the captured state only; (3) the final UPDATE succeeds only while the snapshot still matches; (4) on mismatch the verdict is discarded; (5) the entity stays `pending`/non-public — a discard writes nothing, so the concurrent edit's F-01 invalidation stands and the public gate (unchanged) keeps it invisible; (6) the clear result is `data_changed_retry_required`, returned on the result object, recorded in the audit payload, and surfaced in the admin UI (API consumers receive it in the `data` payload automatically); (7) revalidation cannot resurrect a stale pass — a fresh run captures a fresh snapshot of current data; (8) the offer path uses the identical construction.

**Coverage of the mutation inventory (Stage 04.3 §3.2):** every gate-relevant write changes snapshot-covered state — product fields (row columns), specs (valued-spec count), attributes (uniformly invalidate via `updateProduct`-family paths; attribute rows are not engine inputs, and the F-01 invalidation they trigger is preserved), media add/update/delete (media count), offer create/delete (offer count), offer edits and licence changes (the offer snapshot's own columns). Deliberate exclusions, unchanged from the audited design: `setPrimaryMedia` and variant writes are not verdict inputs (the engine never reads them) — a mid-run `model_ref`-only edit is pinned by test to *not* discard, because the verdict over unchanged inputs remains correct. The guard is intentionally conservative for warning-level inputs (media/offer counts, program status): a warning-only change mid-run also discards — the safe direction, costing one re-run.

**Interleaving test evidence** (`tests/security/validation-concurrency.test.ts`, real DAL + real persistence throughout; the conditional write is never mocked):
- The exact Stage 04.3 product interleaving: begin over a published+passed product → real `updateProduct` clearing the summary → commit reports the computed `passed` with `persistence: 'data_changed_retry_required'`; stored state stays `published`/`pending`; live validation `failed`; product invisible in detail, list, FTS search, **and** alternatives; audit payload records the discard; a fresh run persists `failed`.
- Product arms repeated for a specs wipe and a media add; offer arms for licence expiry (exposure then follows the *current* row: price and destination null) and a price edit (revalidation exposes the *new* price).
- Determinism: two runs begun over unchanged state both persist with the same verdict (products and offers). No-change commit persists normally, including the audit marker `"persisted"`.

## 5. NF-1 — URL host normalization: rules and matrix

**Root cause (Stage 04.3 §6):** the mapped-IPv6 branch matched a dotted-quad suffix, but the WHATWG parser serializes `[::ffff:127.0.0.1]` as `[::ffff:7f00:1]` — the branch was dead code.

**Implementation** (`app/lib/url-policy.ts`): the serialized literal is parsed into its eight 16-bit groups (`parseIpv6Groups`; a trailing dotted-quad is first expanded to its two hex groups so both spellings classify alike; unparseable shapes fail closed). Classification is numeric:
- `::ffff:0:0/96` (mapped) and `::/96` (compatible, which also covers `::` and `::1`): the embedded IPv4 address is judged by the existing IPv4 forbidden ranges — mapped/compatible loopback, RFC-1918, link-local/metadata are rejected; **genuinely public mapped addresses stay allowed** (`[::ffff:8.8.8.8]` accepted, in both spellings);
- multicast `ff00::/8` rejected; link-local `fe80::/10` and unique-local `fc00::/7` preserved (now as group masks);
- DNS names are compared trailing-dot-insensitively: `localhost.` and `foo.localhost.` are rejected like `localhost`; a trailing dot on a public name (`example.com.`) stays allowed (comparison normalized, URL untouched);
- all pre-existing rejections preserved (schemes, credentials, non-443 ports, hex/decimal/octal/short IPv4 — parser-normalized — zone IDs, which the parser itself rejects). Public IPv6 destinations remain usable. No SSRF claim is made: destination URLs are display/link values and are never fetched server-side.

**Test matrix** (`tests/security/url-policy-normalization.test.ts`, 37 tests against the real `validateDestinationUrl` plus DAL/exposure/validation integration): rejected — mapped loopback/RFC-1918(×3)/metadata in dotted, hex-group, and fully-expanded spellings; compatible loopback (both spellings) and unspecified; multicast `ff02`/`ff00`/`ff05`; `localhost.`, `foo.localhost.`, `foo.localhost`; preserved rejections (`::1`, `fe80::1`, `fd00::1`, decimal/short IPv4, credentials, port, http) — all with `reason: 'forbidden_host'` where applicable. Accepted — mapped public (both spellings), public IPv6 (×2), trailing-dot public name, punycode, tracking parameters. Integration: `createOffer` rejects a mapped loopback and accepts a mapped public address; a raw-seeded **passed** offer with a mapped-loopback URL exposes no destination at read time while a mapped public one is exposed; `validateOffer` fails a stored mapped-RFC-1918 destination with an `invalid_url` error.

## 6. NF-3 — timestamp fail-closed: behavior and evidence

**Root cause (Stage 04.3 §4):** `normalizeObservedAt` fell back to `Date.parse`, and when both parsers failed it stored the raw value verbatim — so a Julian-day numeric string (`2461000.5`, a valid instant to SQLite's `julianday()` but unparseable to the shared JS parser) could be stored and later counted fresh by the SQL search filter while the product page hid the same price.

**Implementation:** the gate lives in the DAL choke point. `checkOfferFields` (shared by `createOffer` and `updateOffer`) now rejects any non-null `priceObservedAt` that the ONE shared strict parser (`parsePriceTimestamp`) cannot parse, returning `invalid_observed_at` **before any SQL runs** — no partial offer write, no success audit record. `normalizeObservedAt` was reduced to the strict parser only: it canonicalizes accepted values to `YYYY-MM-DD HH:MM:SS` UTC and returns `null` (never the raw input) for anything else; that fallback is unreachable from the DAL, which rejects first. No second parser was created. Error surfacing follows the existing conventions exactly: DAL conflict/reason → `VALIDATION_FAILED` (400) with a `priceObservedAt` field message in both API routes, and a form error in the admin page (create + update). Null/undefined keep their schema semantics (link-only / field untouched). Parseable *future* timestamps remain storable (freshness is a display/validation concern, already enforced by the shared policy and `validateOffer`) — and are stored canonical, so the engines agree about them.

**Test evidence** (`tests/security/observed-at-fail-closed.test.ts`, 20 tests): `normalizeObservedAt` canonicalizes ISO-Z, ±offset, and SQLite forms to one UTC representation and returns null for Julian/numeric/garbage/empty input; `createOffer` rejects 8 shapes (Julian-day string, numeric string, garbage, invalid month, invalid hour, colon-less offset, whitespace-padded, empty) with **no row created and the `offer.create` audit count unchanged**, and accepts ISO-Z / +02:00 / −05:00 / canonical forms storing the identical canonical instant, plus null (link-only); `updateOffer` rejection is atomic — the stored row (timestamp *and* `passed` verdict) and the audit count are byte-identical afterwards — while a valid patch canonicalizes and still resets the verdict per F-01; display consistency on real stored rows: a future observation evaluates to `future_timestamp`, a 23h59m-old price displays, a 24h01m-old price is hidden as stale (the exact-boundary arithmetic itself remains pinned by the pre-existing 47-test price-policy suite).

## 11. Remaining risks and limitations

- **Discard cost:** a discarded verdict requires an operator re-run; within a single sequential `run*Validation` call the begin→commit window is sub-millisecond-to-milliseconds, so discards should be rare in practice — but under genuine concurrent admin editing they are correct by design, and the UI now says so explicitly.
- **Conservatism:** warning-level inputs (media/offer counts, program status) are inside the snapshot, so a warning-only mid-run change also discards a verdict. Safe direction; documented here so a future auditor does not mistake it for a defect.
- **Non-input changes:** a mid-run change to data the engine never reads (e.g. a spec's text value that keeps the valued-spec count) cannot make a persisted verdict stale, by construction — the verdict depends only on the snapshotted inputs.
- **Carried limitations (unchanged):** route tests invoke handlers directly (true-HTTP coverage comes from the workerd sweep); the CSP `'unsafe-inline'` posture remains post-launch hardening; production ADMIN rate-limiter runtime behavior and genuine expired-JWT replay remain unverifiable without an authenticated production session. Owner actions from Stage 04.3 §14 (Access `/admin/*` extension, fresh Time Travel bookmark) remain owner actions — none was performed.
